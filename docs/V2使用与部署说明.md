# 予舍 V2 使用与部署说明

## 合同模式：先看这一节

合同有“真实”和“演示”两种模式，创建时确定，之后不变。

- **真实模式（默认）**：新合同只接受带服务商回执的签署和资金操作。**本仓库没有接入任何一家电子签署服务或资金服务**，只提供“适配器注册 + 服务端取回执 + 平台复核出款 + 对账 + 补充协议”这一整套流程。部署方用 `CONTRACT_PROVIDER_MODULE` 注册自己的适配器之前，真实合同可以走到“冻结待签署”，但无法完成签署，也不会记录任何入金、拨付或退款。这不是故障，是有意不假装成功：未接入时 `sign`、`fund`、`release`、`refund` 返回 503 `PROVIDER_NOT_CONFIGURED`。
- **演示模式**：启动服务时设置环境变量 `CONTRACT_MODE=demo`，此后新建的合同是演示合同，使用演示签署和模拟资金，页面和合同文本标明“演示”。本地演示、比赛演示、本文“本地隔离验收”一节的脚本都需要它。
- 已存在的合同保持创建时的模式，不随环境变量改变。改动前已签署的合同仍是演示合同（状态 `signed_demo`），照常只读归档。
- 只有精确的 `demo` 才启用演示模式，其他取值（未设置、空、`DEMO`、`true`）都是真实模式。生产环境不要设置它。

**界面**：合同履约工作台按合同模式显示不同的操作。演示合同显示演示签署和模拟资金按钮；真实合同显示“发起电子签署”“发起入金”“申请拨付”“申请退款”、“服务商待办与记录”（含服务商页面链接、同步和撤回）、平台的出款复核与对账，以及已签合同后的“补充协议”。所有状态按服务商回执如实显示：向服务商发起请求不等于已签署或已付款。这套真实合同界面目前只做过类型检查、生产构建和上述隔离服务的接口验收，尚未做浏览器逐页验收。

## 已完成的业务流程

保留户型识别、设计、3D、报价和投标；补回业主竞标表的选定公司入口。

选定承接公司后，业主项目页、公司订单页、平台订单页均可进入同一个合同履约工作台：公司先确认，业主接受或议价；修改后重新确认；三方资料补齐后生成草案、冻结并逐方签署（演示合同为演示签署；真实合同需要服务商回执）。公司保存自己的签约资料与公章，每次用章均需明确授权。已签正文只读，下载件不随后续交易改变。

施工方按阶段提交资料，业主通过或驳回、整改重提。入金后（演示合同为模拟入金），满足验收、余额及争议条件才能拨款。手续费按合同费率计算并记录，重复请求不会重复拨款；争议限制阶段出款，退款保留已验收但未结算的款项。这些规则在两种模式下相同，3% 服务费由乙方承担、按成功结算的阶段计收的规则也没有改变。

经独立处理结果明确解除某个未结算阶段时，平台在处理安排选择解除，该阶段不再允许施工提交或拨款，原验收和处理记录保留，相关未付金额解除保留后可申请模拟退款。签名、公章在签署件中使用绑定合同编号和版本的派生图，不能将原始公章文件作为共享素材。

签约专员提供规则草案、缺项和金额校验；主动点击 AI 辅助复核且配置了现有模型服务后，才进行只读模型复核。未配置时明确显示模型未调用，不影响规则草案。模型不能改合同金额或执行签署、验收和付款。

## 操作顺序

1. 公司在私有签约资料中填写名称、登记资料、授权代表、联系方式，并上传有权使用的公章。
2. 业主选择投标公司，在合同工作台补齐自己的资料和项目面积口径；平台填写自己的签约主体资料。
3. 公司检查金额、范围、工期与阶段表，确认；业主接受或提出议价。议价后由公司重新确认、业主最终接受。
4. 生成规则草案，清理缺项和错误，核对附件与服务费，冻结版本。
5. 三方分别输入签署人，上传本人签名或手写；公司确认本次用章。演示合同的页面持续显示演示签署标识。真实合同点“前往电子签署”后，服务商核验签署人（公司和平台还要核验企业主体与签署授权），签署人在服务商页面完成签署，再点“同步服务商结果”（配置了回调的部署自动同步）；只有服务商的签署回执会记入合同。本仓库没有接入具体服务商。
6. 业主入金（演示合同为模拟入金；真实合同由服务商付款页面完成，回执到达后才记账）；公司提交阶段证据；业主验收或驳回。验收后业主可申请阶段拨款（真实合同先由平台复核，通过后才交服务商执行，复核期间该笔金额被保留），查看服务费及流水。平台可随时与资金服务商对账，对账只报告差异，不改任何金额。
7. 有争议时提交阶段和证据，平台登记独立处理方与依据；相关受限资金不能直接拨付；已交给服务商的出款会标为“暂停”，结果仍以服务商回执为准，出款未结清的阶段不能被解除。已签正文不再修改，变更通过补充协议：业主或公司提出，对方确认，三方（演示合同为演示签署，真实合同为电子签署）签署后才取代对应条款；已提交、验收或结算的阶段不能变更，补充协议有独立的可下载文件。

## 运行与升级

要求 Node.js 24。在项目根目录运行 npm ci，然后配置 apps/web/.env.local，保留原部署中的模型、登录、邮箱等配置，不使用演示口令作为线上口令。`CONTRACT_MODE` 默认不设置（真实模式），只在需要演示合同的环境里设为 `demo`。接入服务商时再设置 `CONTRACT_PROVIDER_MODULE`，值为适配器模块的路径（见下文“正式服务接入边界”）；不设置则真实签署和资金操作保持 503。

验证命令为 npm test、npm run typecheck、npm run build。生产启动命令为 npm run start -w apps/web -- -H 127.0.0.1 -p 3200，由反向代理提供对外访问。

升级前备份现有数据库、上传目录和环境配置。IRENO_PGLITE_DIR 与 IRENO_UPLOAD_DIR 继续指向原部署的绝对路径，新表通过增量DDL建立。PGlite只由单个应用进程打开；停止旧实例后再启动新实例。旧合同及旧分成记录保留，新流程不自动生成旧利润10%分成。已签或已有资金历史的项目不允许直接硬删。

已有会员服务保留为独立业务。新投标按默认3%合同服务费预估，实际以签约版本为准；仅成功的阶段结算产生服务费（演示合同为模拟费用），会员收款不计作工程款。

## 本地隔离验收

本地测试前设置 RUNNER_ENABLED=false，并为 IRENO_PGLITE_DIR、IRENO_UPLOAD_DIR 指定专用新目录。清空测试进程的外部模型和支付密钥，防止既有任务runner或支付权益检查调用真实服务。

scripts/seed-workflow-demo.cjs --isolated-demo 仅允许非生产环境和全新绝对数据库目录，拒绝覆盖已有数据库。它创建一个合成项目及测试账号，不调用外部AI或真实支付。执行时用 node 运行该脚本。**该脚本只建数据，不决定合同模式**：合同在第一次打开合同工作台时才创建，模式取自当时服务进程的 `CONTRACT_MODE`。因此要跑下面的演示签署验收，启动服务时必须带 `CONTRACT_MODE=demo`。

合成业主账号19900000001、公司账号19900000002、无关测试账号19900000003，测试口令均为DemoOnly2026!。这些账号只存在于专用测试库，不能用在正式服务。平台账号由该测试进程的BOSS_PHONE/BOSS_PASSWORD单独配置；HTTP验收脚本默认使用19900000000及DemoBossOnly2026!。SESSION_SECRET请单独配置测试值，HTTP本地测试设置COOKIE_SECURE=false。

先运行种子脚本并结束该进程，再启动指向同一测试目录的Next服务（演示验收需带 `CONTRACT_MODE=demo`），仅监听127.0.0.1。默认3301端口可执行 node scripts/workflow-http-smoke.cjs；其他端口用WORKFLOW_TEST_URL指定。该脚本只允许回环地址，需新种子数据，重复运行应换新测试库。**不带 `CONTRACT_MODE=demo` 时，该脚本会在第一次演示签署处得到 409 `MODE_MISMATCH` 并失败，这是预期行为**，用它可以验证真实合同确实不接受演示动作。不要直接对线上运行旧acceptance、AI-e2e和payment-smoke脚本。

`scripts/contract-real.test.cjs` 是真实合同领域规则的单元测试（16 项，已并入 `npm test`），不依赖服务和数据库；`scripts/workflow.test.cjs` 在演示模式下跑原有的合同测试。`scripts/contract-provider.test.cjs`（33 项，已并入 `npm test`）覆盖服务商请求、回执入账、出款复核、对账、补充协议和导出。

`scripts/contract-provider-http-smoke.cjs --isolated-demo` 是真实合同的 HTTP 验收（26 项检查）：在 `npm run build` 之后，它自带临时数据库，用不带 `CONTRACT_MODE` 的生产服务走完“服务商签署、回调、入金、出款复核、对账、补充协议、争议”。其中的服务商是仅供测试的替身 `scripts/test-contract-provider.mjs`：会话和付款存在临时目录的一个 JSON 文件里，由验收脚本扮演签署人和付款人；它只在 `CONTRACT_PROVIDER_TEST_ONLY=1` 且状态文件位于系统临时目录时才加载。**它不是真实服务商，不连接任何外部服务，不要把 `CONTRACT_PROVIDER_MODULE` 指向它去运行真实用户使用的服务器。**

## 正式服务接入边界

**已有**：真实模式的数据结构、规则和服务端流程。签署需要带“已核验签署人”的服务商回执和证据摘要，资金变动需要金额一致的成功回执，同一回执不能重复使用；没有回执就拒绝，不降级成演示。`packages/shared/src/contract-providers.ts` 定义了签署服务和资金服务两个适配器接口（字段通用，不属于任何一家服务商）和注册函数。服务端流程已接通：路由收到 `sign`、`fund` 或出款复核通过后，在数据库锁之外调用适配器创建服务商会话或付款，把服务商页面链接只返回给发起人；回执只由服务端向服务商查询（点“同步服务商结果”触发 `POST /api/orders/:id/workflow/sync`，或由服务商回调 `POST /api/contract-providers/signing|payment/callback` 触发，回调只指明查哪一笔，正文不会写入合同）；平台通过 `POST /api/orders/:id/workflow/reconcile` 对账。每笔拨付和退款先经平台复核，复核前保留对应金额。这些流程已用上文的测试替身服务商在隔离服务上验证。

**没有**：任何一家真实服务商的接入。仓库里没有任何电子签署、实名核验、资金托管、分账服务的适配器实现，也没有真实回调验签。要上线真实合同，部署方需要：选定并签约电子签署服务和有资质的资金服务（银行存管或持牌支付机构）；实现 `SigningProvider`、`PaymentProvider`（含自己的回调验签 `verifyCallback`），导出为一个模块 `{ signing, payment }`，并在启动服务时用环境变量 `CONTRACT_PROVIDER_MODULE` 指向它（由 `apps/web/instrumentation.ts` 在服务启动时加载注册，加载失败只记日志，真实操作继续返回 503）；让服务商的签署证据绑定冻结条款摘要；取得经审查的合同模板和适用的法律意见。合同条款的法律效力不由本仓库保证。上线前还应在服务商的沙箱里用真实适配器重跑一遍验收，替身服务商的结果不能代表真实服务商的行为。

演示合同里的签名图片、公章和模拟资金流水仍是可追踪的演示记录，不是可靠电子签署、身份认证或第三方资金托管。

外部参考图链接会提示远程内容未冻结；上传的受限图片才能进入版本快照。多实例数据库没有伪装为已实现。

本次只修改本地源码，未更新远程网站。交付源码包不含node_modules、Git历史、构建缓存、数据库、私有上传或实际.env配置。


### 一人付独立会员付款（2026-11-15）

新版会员购买复用原公司登录态、会员页和权益刷新流程，服务端安装opcpay 0.3.5，仅从opcpay_api_key读取密钥；不再使用YIRENFU_API_KEY。并行实例配置固定MEMBERSHIP_PAYMENT_NAMESPACE和PUBLIC_BASE_URL（新版为HTTPS 8443），不得在已有购买记录后随意更换前缀。

实测独立项目“予舍”已启用39元/月基础时长套餐。SKU从实际product响应选择，服务端只接受与既有基础月会员相匹配的唯一套餐；商户改价、改收费模式或出现多个匹配套餐时拒绝购买，需要先同步业务规则与页面，不能悄悄改收费方式。购买前核对capabilities，不把未开放功能显示为可用。当前套餐不需要次数/积分核销；requires_consumption=true时拒绝直接凭余额开通。

purchase_intent字段在原会员付款表保存用户标识、SKU、返回地址和固定购买编号，写入成功后才发起购买。同一未确认记录并发复用；超时/未知结果保持原参数重试，不换号；明确入口过期才允许新建记录。复制的旧站付款记录不参与新版购买或权益确认。返回页面、扫码、READY都不等于已付款，仅服务端access确认权益后开放服务。entitlement_confirmed仅表示观察到权益，不是逐笔支付回执。

该项目能力查询显示交易状态查询可用、退款/退款查询/账单/交易列表未开放；会员支付不是工程款托管适配器。未实付、未真实核销、未验收生产回调。已读取SDK随包文档与技能；真实完整付款验收需由用户自行完成一笔购买后确认权益和重复刷新行为。该判断的退款与账单部分已由下一节的站内流程补充，但一人付官方接口仍未开放。

### 同一订单保留两份合同

合同工作台顶部可选择“演示合同”或“真实合同”，两份均可独立确认、签署及记录履约。首次进入另一模式时创建新合同，不继承已签名、模拟资金、验收记录或补充协议。旧合同始终保留；切换查看不会把演示凭证转换成真实凭证。

CONTRACT_MODE 仅决定最初创建的合同默认模式，无需为页面切换重启服务。新增 contract_workflow_variants 表由启动流程自动创建，不修改原表主键或旧合同内容。升级前按既有部署规范备份数据库；真实签署及资金操作仍须部署真实服务商适配器。

### 会员付款账单与退款（2026-11-15）

一人付的退款、退款查询、官方对账账单和交易列表四个接口目前都未开放（2026-11-15 用线上密钥只读核对：`capabilities` 对应开关全为 false，四个接口返回 501 `CAPABILITY_NOT_AVAILABLE`）。因此本站不能通过接口发起退款，也拿不到官方对账单。已开放的只有单笔交易状态查询 `transactions/query`，本站只用它。

账单：装修队在会员页点“付款账单 / 退款”，老板在“会员与入驻”页查看全部。每条记录用保存的购买用户和购买编号调用 `transactions/query`，状态为 `PAID` 已支付、`PENDING` 待支付、`REFUNDED` 已退款、`UNKNOWN` 待确认；404 记为“支付服务无此记录”；读取失败保留上次结果并提示。该接口返回的是后台最近一次验签结果，不是实时查单，所以页面显示“最近核验”时间；同一记录 15 秒内不重复读取，每次最多刷新 20 条。接口不返回实付金额、到账金额和支付时间，汇总里的金额是本站记录的套餐价（39 元），只统计一人付已核验为 `PAID` 或 `REFUNDED` 的记录；旧站复制的和线下记录标为“旧站/线下记录”，不参与统计。这份账单不是支付宝官方对账单。

退款流程：只有已核验为 `PAID` 的付款才能申请，原因 5–200 字。申请后装修队可在平台处理前撤回；老板同意或驳回，处理意见 2–200 字必填。**同意只记录平台决定，不会退钱，也不会取消会员权益**：款项需平台在支付宝侧人工退回，只有一人付查询返回 `REFUNDED` 才把该笔标为已退款并关闭申请。`REFUNDED` 是终态，之后读到 `PAID` 不会重新打开；一人付先于本站申请就已退款的，也会按提供方状态记录为已退款，操作人标为提供方。每步写入申请记录的历史。

数据库：`membership_payments` 新增 `transaction_snapshot`、`refund` 两列（jsonb），启动时 `ADD COLUMN IF NOT EXISTS` 自动建立，不改旧列和旧记录。回退只需不再使用这两列。

等一人付开放退款接口后，只需在老板“同意”之后调用 `refund()` 并保存其返回单号，`recordPaymentTransaction` 与页面不用改；开放前不要把本站记录当作已退款证据。
